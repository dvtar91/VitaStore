# 1. Целевая Cloud-Native архитектура

## Ключевые решения

1. В магазине нет полноценного сервера и серверной СУБД.
2. Касса становится лёгким приложением на управляемом планшете.
3. Для офлайн-продаж используется локальный зашифрованный кэш устройства, а не Local DB сервера.
4. Работа с ККТ и терминалами вынесена из POS в **Edge HAL Agent**.
5. POS работает с единым контрактом HAL, не зависящим от производителя оборудования.
6. Различия терминалов изолированы в сменных адаптерах.
7. Серверная часть платежей централизована в Payment Gateway.
8. SAP остаётся master-системой и интегрируется с Cloud Backend через API/iPaaS, а не FTP.

# 2. Работа с разнородным оборудованием

`Thin POS App` не обращается напрямую к USB/COM-портам и не содержит драйверов. Он вызывает стабильный локальный контракт `Edge HAL Agent`, например:

```text
POST /fiscal/receipts
POST /payments
POST /payments/{id}/cancel
GET  /devices/health
```

HAL определяет профиль магазина и загружает нужный адаптер: ARCUS-2, Ingenico, Verifone либо драйвер конкретного фискального регистратора. При замене устройства меняется конфигурация или плагин HAL, а не POS. Серверный `Payment Gateway` отдельно абстрагирует протоколы банков и эквайеров, обеспечивает токенизацию, маршрутизацию, отмены и сверку. HAL при этом решает локальную аппаратную интеграцию, а Payment Gateway — интеграцию с платёжным провайдером.

# 3. Offline-mode и восстановление связи

Перед началом смены `Store Sync Service` передаёт на планшет подписанный версионированный snapshot ассортимента магазина: SKU, цены, штрихкоды, налоги и ограниченный набор промо-правил. Snapshot и очередь операций хранятся в зашифрованной SQLite/IndexedDB на планшете. При обрыве связи POS продолжает наличную продажу: рассчитывает цену по последней валидной версии, передаёт чек в локальный HAL, а фискальный регистратор фискализирует и печатает документ. Безналичную оплату и списание баллов следует разрешать офлайн только при наличии отдельно согласованного режима эквайера и риск-политики; по умолчанию гарантируется именно наличная продажа.

Каждый offline-чек получает глобальный `operationId`, номер кассы, монотонный локальный sequence number, версию каталога и время устройства. После восстановления сети Sync Agent передаёт события пакетами в исходном порядке. Облако дедуплицирует операции по `operationId`, сохраняет чек один раз, обновляет остатки и публикует события в SAP и Smart Fulfillment. Сервер возвращает подтверждённый watermark, после чего локальные записи можно удалить. Для уже напечатанного фискального чека цена ретроспективно не изменяется; конфликты остатков и устаревших справочников регистрируются для последующей сверки, а не блокируют повторной обработкой завершённую продажу.
